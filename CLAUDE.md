# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**MALE** is a browser 2D game engine written in plain JavaScript on top of p5.js. There is no build step, no bundler, no package.json and no module system: every file is a classic `<script>` that declares globals. Pages are designed to run **straight from disk (`file://`)** as well as over http, so avoid `fetch`, ES modules, or anything that breaks on `file://`.

## Running

- `index.html` is the home page / game picker (plain HTML, no engine scripts; it is the GitHub Pages landing page). It links to `shooter_demo.html` (entry: `shooterGameDemo.js`) and `world_of_theaya.html` (entry: `world_of_theaya.js`). Each game's pause menu has a "Return to Home Page" button that goes back to `index.html`. To add a game, copy a game page, change its last `<script>` tag, and add a card to `index.html`. `main.js` is an older debugger-scene demo and `blank.js` is a scratch file.
- Run the YAML embed sync while editing `.yaml` files: `node tools/syncDevFiles.js --watch` (one-shot: drop `--watch`). It rewrites `male/devFiles.js`, which is auto-generated, so never edit it by hand.

## Tests

The tests run in the browser; there is no CLI runner. They live in `male/unitTests.js` and need every engine class loaded, so they only work inside a page.
- In the browser devtools console: `runUnitTests()` (runs and logs a report), or `UnitTests.run()` for the structured result (`.testsFailed` lists failures).
- Running one suite: there is no filter. Call `UnitTests.suite(name, fn)` / `UnitTests.test(name, fn)` / `UnitTests.assert` from the console, or temporarily comment out the other `testX()` calls in `run()`.
- New suites go in a `testX()` function that `run()` calls. `blank.js` and `main.js` are deliberately not tested.

## Architecture

**Script load order matters** (see `shooter_demo.html`): `libs/p5.js` → `libs/MAL_Graphics_Engine.js` → `male/Global.js` → `helperFunctions.js` → `inputs.js` → `Camera.js` → `item.js` → `objects.js` → `scene.js` → (`MALEngine_Encryption.js`, only on pages that use it) → `yaml.js` → `devFiles.js` → `devConsole.js` → `unitTests.js` → game file. Later files rely on globals from earlier ones.

**Game file pattern**: the game file defines p5's `setup()`, which does `world = new World(tickLength)`. Game objects and `new Scene(...)` are usually created at the top level of the game file, *before* `setup()` runs. Objects register themselves in static registries (`shell.allObjects`, `gameObject.objects`, `Hitbox.objects`, `UI.objects`, `Scene.scenes`), and each one names the scene ids it belongs to through trailing `...scenes` constructor args. Pick the shown scene with `Scene.setScene(id)`.

**World (`male/Global.js`)**: owns its own `requestAnimationFrame` loop. It does not use p5's `draw()`, so don't define one. The loop has two cadences:
- **Fixed-timestep ticks** (`tickLength` ms, default 20): `DevConsole.tick()` → controller update → `Scene.tick(dt)` → global `main()` if defined → syncing and cleanup of the object registries. Game logic and physics belong here.
- **Render every frame**: `Scene.render()` → `DevConsole.render()`.
- **Looking away**: `world.whenHidden` (tab hidden or browser minimized) and `world.whenUnfocused` (another program focused while the page still shows) are each `'run'` or `'pause'`. `'pause'` freezes ticks and drops the time away (nothing is caught up), but a visible page keeps rendering. In a hidden tab rAF stops, so `'run'` is driven by a Blob Worker timer that sends a step every tick (`world.backgroundTimer` is `'worker'`). If the browser refuses the worker, a throttled `setInterval` backup runs the missed ticks in bursts of up to `world.backgroundCatchUp` seconds (`backgroundTimer` is `'interval'`). Hidden tabs render `world.backgroundFps` times a second (default 0). Hooks: `onHidden` / `onShown`, and `onFocusLost` / `onFocusGained` for window focus only (tab switches don't count). `runInBackground` is an older alias for `whenHidden`. The shooter demo uses `onFocusLost` to open its pause menu.
- `World` has static getters (`World.mouse`, `World.tick`, `World.camera`, …) that pass through to `World.active` for older code. New code should use the instance (`world.` / `this.`). `window.mouse`, `window.keyboard` and `window.controller` are global aliases too.

**Scene (`male/scene.js`)**: `new Scene(id, backColor, ...scripts)`. How a script runs depends on its type:
- A **function** script runs every **render frame**, for HUD and drawing.
- An **object** with `exe` / `call` / `callback` / `function` runs every **tick** as `(dt, scene)`.

Every object's `update(dt)` and its `obj.scripts` (functions called with `(obj)`) run on ticks. `scene.pause` freezes updates for objects that don't set `ignorePause`, but rendering continues. `scene.time` is a clock that pauses with the scene, and timers such as `throttle` / `gameTimeout` read it. Draw order: game objects by `layer`, then `uiObjects`, which are always drawn on top.

**Object hierarchy (`male/objects.js`)**: `shell` (registry/ids) → `geometryObject` (holds a `Transform` plus a `Renderer`) → `Hitbox`, `genericObject`, `gameObject`, `UI` / `Button`. `UI` → `uiButton`, `uiTextBox` (a typed text field: a hidden `<input>` does the editing, so all native shortcuts and IME work; while it has focus `getInput` hides the keyboard; it can be drawn by hand with `box.render()`). Then `gameObject` → `Entity` (which takes behaviour bundles through `entity.package(Entity.Packages.living(), ...)`) → `Player`. Hitbox shapes are `rect`, `circle`, `ellipse` and `triangle`. The collision math lives in `helperFunctions.js`. Collision resolution is a known weak area (see `notes.txt` and `todoList.yaml`).

**Items (`male/item.js`)**: `Inventory`, plus the `Item` class. An item is built from components: subclasses of `ItemComponent` (`Durability`, `Attack`, `Mining`, `Ranged`, `Firearm`, `Placement`, `Ability`, …) whose constructors take their values. Add them with `item.package(new Durability(500), Item.Packages.melee(...), …)`, which works like `Entity.package`. Read them with `item.get('attack')` / `item.components.attack`. Hooks are methods on the component (`canUse`, `onUse`, `onTick`, `onPlace`, `onBreak`, or any `onX` for `item.emit('x')`). Item types are plain subclasses whose constructor calls `super(name)` and then `this.package(...)`, for example `Weapon` → `Sword`, `Tool`, `Armor`, `Consumable`, `Placeable`, `Skill`, `Gun`. Every constructor parameter (component or item) needs a default, because `Item.fromJSON` calls `new Type(name)`. `clone()` doesn't call the constructor; `_afterBuild()` sets up runtime state. `Gun` owns the bullets in flight (`Gun.bullets`).

**Input (`male/inputs.js`)**: read input through `getInput('key@r')`, `getInput('key@shift')`, `mouse@left`, `stick@left:x`, `button@...` and so on. `KeyboardStick` gives a virtual analog stick. Default bindings are in `world.defaults.binds` (`action -> { keyboard, controller, mobile }`): define a game's with `world.defineBinds({...}, { replace: true })`, change one with `world.setBind(action, input)`, and read one with `getInput('default@<action>')` (lower-case action ids). When the DevConsole is open, `getInput` returns neutral values.

**DevConsole (`male/devConsole.js`)**: only active after `world.setDebugMode(true)`. The `` ` `` key toggles it. Extend it with `DevConsole.registerCommand({...})` / `registerDisplay({...})`. `/display todoList` renders `todoList.yaml`, parsed by the small custom YAML reader in `male/yaml.js`. `documentation.md` has the full command and todo-file reference.

**Graphics/audio (`libs/MAL_Graphics_Engine.js`)**: a standalone image, sprite and audio library with the global `MAL` / `MAL_Graphics_Engine`. It does not depend on the engine files. The root `README.md` is its documentation. Angles are in **degrees**. On `file://`, `getPixel` / `toDataURL` return null and p5 WEBGL can't use image textures. Browsers block audio until the user interacts with the page. `male/graphics.js` (`Song`) is an unfinished wrapper and is not loaded by the HTML pages.

**Sealed data files (`male/MALEngine_Encryption.js`)**: standalone too (no engine dependency, also runs in Node), global `MALEngine_Encryption` / `MALCrypt`. It turns any JSON value (or bytes) into a `.malengine` file: compressed (LZ77), encrypted (ChaCha20) and sealed with HMAC-SHA-256 over every byte, so an edited file throws `MALEncryptionError` (`err.code` `'tampered'`, `'wrong_type'`, `'not_malengine'`, …) instead of loading. It is all synchronous plain JS on purpose (WebCrypto is async and missing on `file://` / plain http). `encode(data, { key, type })` / `decode(bytes, opts)`, `save(data, name, opts)` downloads, `pickFile()` / `load(file, opts)` / `pickAndLoad(opts)` read files back, `toBase64` / `fromBase64` for storage. The format and its limits (the key lives in the game's code) are documented at the top of the file.

## Conventions

- Class names are mixed case (`gameObject`, `shell`, `uiButton` next to `Player`, `Scene`). Keep the existing names, because the registries and `world.defaults.classes` refer to classes by name.
- Custom error classes (`gameObjectError`, `hitboxError`, `sceneError`, …) live at the top of `Global.js`.
- To print to the in-engine log, use `new Message(text)`.

## Adding content to World of Theaya

`world_of_theaya.js` creates every item, block, food, station, creature, crop and skill from a plain spec object with one function: `defineElement(spec)` (or `defineElements([...])`). The field list is the doc comment at "3b. Game elements"; the game's own content (search for `defineElements([`) is written the same way. Types: `item`, `block`, `terrain`, `food`, `crop`, `creature`, `workbench` (a recipe menu, a machine when `slots:{input, output, fuel}` is an object, or a station with its own menu via `panel:{ draw(s, block, L), w, h }` like `heart_stone`), `container` (`slots: n`), `skill`, `upgrade`, `structure` (something built into the world at generation, like the forest-only `goblin_camp`: `biomes`, `count`, `radius`, `parts` laid out in hex rings / axial offsets, a `heart` block that keeps its `creatures` respawning; `respawn:{ days, count, dist }` builds new ones when none of the type has stood for that many game days; `Structures` in section 7 places, ticks and saves them). Drops are `[{ id, chance, amount:[min, max], linked, priority }]`, or `{ choose:[ids], amount }` for random picks (each unit one of the ids). A block spec can draw itself with `draw(g, def, block, c, poly, i)`. Creatures have a `teamwork`: `'selfish'` (default, the per-creature `MOB_AI`) or `'group'` (`GROUP` tactics in `Mobs.groupThink`: call, muster, surround, archers, falling back to heal while another enemy covers it); `roles` give them gear (`ARMED`, goblins). AI levels (`MOB_AI`, rolled per creature from its `ai` odds): `dumb`, `smart` (looks after itself), `genius` (decides like a player: `GENIUS`, `Mobs.geniusThink` / `readFight` size up the fight and keep a plan, `m.plan`: fight, wait for an opening, or recover, which means getting away and only coming back at full health). A creature with `lays:{ block, every, radius, max }` lays that block in its cell now and then (`Mobs.layTick`): chickens lay `egg`, a walk-over block of kind `pickup` (a `b.count` clutch) that is picked up by hand (`pickUpBlock`). Creatures of the dark burn in the sun and keep to caves in daylight, except while a weather with `shade` (rain, storms) hides it (`Mobs.sunOut` / `sunIn`). Stack sizes come from one category rule (`STACK` / `STACK_OF`) and a spec's `stack` only overrides it. Stations register themselves in `STATION_TITLES`, `CRAFT_STATIONS`, `MACHINES` and `STATION_DRAW`, which the UI, ticking and cell tracking read. Recipes written in a spec (`recipe`, `recipes`) are queued and added once the `Recipe` class exists (`Content.flush()`); other recipes still use `Recipe.add` in section 5. Natural block families (`naturalMaterials`), ores / metals / tools / armor (generated from `materialList`) and the weather table stay in their own tables.

Every station's recipe list has a search bar (hand crafting, workbench, kitchen table, forge, cooking pot, drying rack); only the loom opts out with `search:false` in its spec (`NO_RECIPE_SEARCH`). Food: the kitchen table (`workbenchTag:'kitchen'`, recipes in section 5 "Kitchen table") is a plain recipe menu for dishes that need no heat; the cooking pot does the heated ones. A machine's input slots hold one kind of ingredient each (the pot has 4, a canteen of `@water` counts as one), so a machine recipe must never list more than 4 kinds. A food's `thirst` restores thirst; tag it `'drink'` (smoothies and juices at the kitchen table, teas in the pot, milk) and it's drunk instead of eaten. No two pot recipes may use exactly the same kinds of ingredients (a load-time warning catches it). Base foods are kept plain and low; `fine_food` dishes with `instantHealth` / `regen` reward more ingredients.

Textures are optional (section "3a. Textures"): a spec's `texture` field, the `TEXTURES` table (keyed by element id, including generated ones, ground floors and `'player'`), or `Textures.set(id, tex)`. Every world draw site falls back to the built-in procedural look when there's no texture or the image hasn't loaded. HUD drawing (item icons, menus) is never textured.

Mouse cursors: the images are in `Assets/world_of_theaya/cursors/` (24 / 32 px, plus 48 / 64 px for high-DPI screens; hotspots are in its `cursors.json`). They are drawn at 24 px (`Cursor.size`; 24 and 32 exist, each with a double-size copy). The `Cursor` module (section 3a) chooses one every frame in `hudLayer.render` (`Cursor.update()`) from the HUD region under the mouse (a region with `text: true` gets the text cursor) or from the left-click quick action (`GameUI.quick`). A quick action can name its own cursor with a `cursor` field. Don't call p5's `cursor()` in this game, since `Cursor` overwrites the canvas cursor each frame.

Controls: every action's default bind is in `THEAYA_BINDS` (keyboard) and `THEAYA_PAD_BINDS` (controller), installed through `world.defineBinds` in `setup()` by `Binds.install`, and read as `Keys.pressed('default@<action>')`, never a raw key; `Keys` checks both devices, so either works at any time. The Controls panel (pause menu > Settings > Controls) has a page per device and rebinds them (`Binds.set(action, input, save, device)` swaps when a bind is taken, so no two actions of a device share one) and saves changes in `theaya.settings`. With a controller, `Pad` moves an on-screen cursor with the `cursor` stick (it writes `mouse.rawX` / `rawY`, so game code keeps reading the mouse), its `move` / `wheel` binds also count as `mouse@left` / `mouse@right` for menu clicks, and sneak toggles (`Pad.sneak`). In menus `PadNav` works like a console game: the other stick jumps the cursor to the next HUD region of the top menu (slots, buttons, sliders; the action wheel picks the option in the stick's direction), the `interact` bind selects it (a left click), and with a station open the bumpers switch between it and the backpack. It reads `GameUI.regions`, so anything drawn with `region()` / `button()` / `drawSlot()` is reachable. Settings > Input device (`InputDevice`, saved as `Settings.data.inputDevice`) picks what the game listens to: `auto` (both, the default), `keyboard` (the controller is ignored) or `controller` (while one is connected, a window capture-phase listener drops the real mouse's events and `Keys` ignores the keyboard). Read input through `Keys` / `Pad.enabled()` so the setting applies. `Binds.shown(action)` / `keyVars()` give the bind of the device in use. Only menu clicks (left mouse), Shift+click and the mouse wheel use fixed inputs. Text that names a key takes it from `keyVars()` (`{inventory}`, `{close}`, …). Tutorial text goes through `TK()` instead of `T()`, which adds those plus `{hotbar}` and `{moveDo}` / `{wheelDo}` (and `…Low` forms) for pointing at a cell ("Left-click the stone" / "Press Q on the stone"), so never write a literal key in a `tut.*` text.

Difficulty (Settings > Difficulty, or the start menu's New Game screen, both drawn by `drawDifficultyPicker`: `easy` / `normal` / `hard` / `brutal`, saved in `theaya.settings` and in every save as `data.difficulty`): each level in `DIFFICULTY` is a table of multipliers, read with `Difficulty.mult(key)`. Run new random rolls through it as well. Chances that help the player go through `Difficulty.luck(c)` (drops, loot, gear drops) and chances that hurt go through `Difficulty.bad(c)` (food poisoning, storms and droughts). AI odds go through `Difficulty.shiftAi`. A structure spec with `hostile: true` has its count and respawn times scaled.

Saved games (section "12c"): pause menu > Save Game downloads a `.malengine` file (`SaveGame.capture()` → `MALEngine_Encryption.save` with `SAVE_FILE.key`). Start menu > Load Saved Game, pause menu > Load Game, or a file dropped on the page checks the file, keeps it in `sessionStorage` (`SaveStash`) and reloads into `#load`: the world is generated from the save's seed and `SaveGame.apply()` lays the saved state over it at the end of the file, before the first frame. A save holds every cell (blocks with their state: `Box` contents, machines, farmland seedlings), the clock, weather, player, inventory, armor, levels, skills, creatures (with their gear) and structures (`Structures.capture()` / `load()`); items keep only what differs from a fresh `Items.create(id)`. **New world state that should survive a save has to be added to both `capture()` and `apply()`**; scene-clock deadlines (`sceneTime()`) are saved as time left, game-clock ones (`Clock.elapsed`) as they are. Every save is stamped with `GAME_VERSION` (`'0.5.x'`, as `data.gameVersion`; unstamped saves count as 0.5.0). A save from an older patch of the same major.minor is brought up to date on load by `SAVE_PATCHES[x]` (one fix-up per patch number, run in order by `SaveVersion.upgrade`); a newer save, or one from an older major.minor, is refused. For a small change to what a save holds, bump the patch in `GAME_VERSION` and add its `SAVE_PATCHES` entry. Bump `SAVE_FILE.version` when the layout changes in a way older code can't read. Never change `SAVE_FILE.key`: it would make every existing save unreadable.

Dutch (Nederlands): its texts live in `world_of_theaya_text_nl.js` (loaded after `world_of_theaya_text.js`), which adds a `dutch` text to every `THEAYA_TEXT` entry from `THEAYA_NL_TEXT` (key -> string; a key with no Dutch shows its English), plus `THEAYA_NL_NAMES` for fixed names and `THEAYA_WORDS_NL` (`adj` / `noun` / `thing`) for generated ones (`_dutchName` in `world_of_theaya.js`: `iron_pickaxe` -> IJzeren houweel). A new text key needs a `dutch` line in `THEAYA_NL_TEXT` too.

Text and languages (English + Japanese + Dutch): never put on-screen text in `world_of_theaya.js`. Every string lives in `world_of_theaya_text.js` (loaded in the page's `<head>`, before the engine) as `THEAYA_TEXT['key'] = { english, japanese }`, registered with the World language system in `setup()` (`world.addDialog`). Show it with `T('key', { vars })` (`{name}` placeholders; `{s}` is the English plural). Names of items, blocks, creatures, skills, biomes, weather and months come from `nameOf(id)`: Japanese uses `THEAYA_NAMES`, or builds generated ids from `THEAYA_WORDS` (`iron_pickaxe` → 鉄のツルハシ), so a new material or crop only needs its word added. A kanji in a Japanese name also needs its hiragana reading in `THEAYA_READINGS` so the crafting search (`NameSearch.matcher`) finds it by how it's said (斧 / おの / オノ / `ono`); a missing one prints a console warning the first time it's searched. Block / creature / skill `def.name` and `STATION_TITLES` / `MACHINES` texts are getters that follow the language; station texts are `station.<station>.<field>` keys, creature actions `action.<creature>.<key>`. Don't name a local variable `T`. The language is picked in the Settings menu (pause menu > Settings, or the start menu toggle), saved in `localStorage` (`theaya.settings`), and otherwise follows the browser.
